# The ROG Strix G533ZW

The machine tw was written on: what it is, what was measured on it, what

2026-11-13 to 2026-11-15. Its settings in tw are

## The machine

| | |
| --- | --- |
| Model | ASUS ROG Strix G533ZW (DMI board name `G533ZW`), 20 CPU threads, 16 GB |
| Panel | `eDP-1`, 1920x1080, used at scale 1.25. Two modes: 300 Hz (preferred) and 60 Hz |
| GPUs | Intel drives the panel and two DisplayPort outputs (most likely the USB-C ports). NVIDIA RTX 3070 Ti drives HDMI and one DisplayPort |
| Battery | holds 54 Wh of the 90 it was designed for; charge limit at 100 |
| Thunderbolt | one Thunderbolt 4 port, security level `user`, `iommu_dma_protection` 1 |
| Bluetooth | Intel, on USB (`8087:0033`), driver `btusb` |
| Disk | the system runs from an external USB SSD (`sda`, a Samsung T7: `/boot` on `sda1`, an XFS root on `sda2`), not encrypted. The internal NVMe disk holds another install and is not mounted |
| System | CachyOS, Limine boot loader (`limine-mkinitcpio` rebuilds the boot image; the kernel command line is `KERNEL_CMDLINE` in `/etc/default/limine`), dbus-broker, fish |
| Sleep | `s2idle`; the firmware offers `deep` as well. Swap is zram only, so it cannot hibernate |

It came with KDE. Since 2026-11-15 there is no login manager (a text
console, then `tw-session`), Wi-Fi is iwd, the keyring is oo7, and KDE,
NetworkManager, power-profiles-daemon, fnott and `alsa-plugins` are
removed. [system.md](system.md) has each of those as a step.

## Decisions

The owner's about this laptop, with their reason where they gave one. Do
not reopen them unasked. Their decisions about tw itself are in
[CLAUDE.md](../CLAUDE.md#working-with-the-owner).

- **Sleep stays off.** The one suspend under tw did not wake (see
  [Sleep](#sleep)). Asked whether to find out why or leave sleep off:
  "Leave sleep off". Suspend is of little use to them anyway: "if it's
  asleep or locked nothing is getting done anyway".
- **The case to optimise is the Claude app working for hours** with the
  owner at the machine, on battery.
- **Huge pages stay on**, for performance.
- **Of the kernel settings offered, the two sysctls, the `xe` blacklist and
  the NVMe queue depth** were taken. A smaller swap device,
  `cgroup_disable=memory` and a smaller watermark distance were not.
- **boltd is replaced by the udev rule**, because a Thunderbolt dock is in
  occasional use ("my computer doens't have enough usb inputs").
- **Builds stay as fast as the machine allows.** A memory saving that costs
  compile speed is declined, and the figure in `btop` is not worth one.
- **Left as they are:** avahi (KDE Connect), `systemd-timesyncd`,
  `systemd-resolved`.

## Memory

The owner reads memory off `btop`: the "used" total at startup, and the
per-program lines. Both mislead in ways worth knowing before answering a
question about them.

### How to account for it

When asked where the memory goes, account for the whole machine before
looking at tw. The figure `btop` and `free` call "used" splits into parts
that add up to it, all from `/proc/meminfo`:

| Part | From `/proc/meminfo` |
| --- | --- |
| used | `MemTotal - MemAvailable` |
| held back: free memory and cache the kernel does not count as available | `MemFree + Active(file) + Inactive(file) + SReclaimable - MemAvailable` |
| kernel bookkeeping | `SUnreclaim + KernelStack + PageTables + SecPageTables + Percpu` |
| shared buffers (screen and windows) | `Shmem` |
| programs, each for itself | `AnonPages` |
| kernel, outside every counter: drivers, modules, the swap table, pages parked per CPU | what is left of "used" |

Per program, `RssAnon` in `/proc/<pid>/status` is what it holds for
itself, and `smaps_rollup` has the rest; `drm-total-*` in
`/proc/<pid>/fdinfo/*` counts its GPU buffers. The pages parked per CPU are
the `count:` lines of `/proc/zoneinfo`, in 4 kB pages.

Two things that are easy to get wrong, and worth saying with any answer:

- **"Used" is MemTotal minus MemAvailable**, and a good part of it is in
  use by nothing: the kernel leaves its own reserve, a slice of the page
  cache and half of the reclaimable slab out of MemAvailable.
- **A program's line in `btop` is resident memory**: what it holds for
  itself plus every library page it has mapped, most of which other
  programs share and which is file cache. `RssAnon` is what each program
  holds for itself. Twelve systemd processes add up to
  109 MB of lines and hold 18 MB: the difference is one 6 MB library that
  each maps and `btop` counts again in every line.

`btop` cannot show steps under about 40 MB: the reading swings by more
than that from one boot to the next, because the pages parked per CPU were
anywhere from 55 to 97 MB in the first minutes. Compare the parts above,
one by one, instead.

### Where it was

About 900 MB at startup with nothing but a terminal open (measured: 893).

| Part | MB | What it is |
| --- | --- | --- |
| Held back | 285 | free memory and cache the kernel does not count as available: the zones' watermarks and low-memory reserves (172, large because transparent huge pages raise `min_free_kbytes` to 66 MB), 82 of page cache, half the reclaimable slab |
| Kernel, outside every counter | 302 | 61 the swap device's table (zram: 16 bytes per page of a device as large as the RAM, used or not), 42 the loaded modules, 12 other vmalloc, 65 free pages parked per CPU, and about 160 that drivers took straight from the page allocator |
| Kernel bookkeeping | 143 | slab, stacks, page tables, per-CPU data |
| Shared buffers | 57 | tw's three screen buffers and the terminal's |
| Programs | 107 | tw 19, the terminal and its shell 12, the rest daemons |

Nobody can say whose the 160 MB of driver pages are: the kernel is built
without `PAGE_OWNER` and `MEM_ALLOC_PROFILING`. One lead, never followed
up: XFS keeps its metadata buffers outside the page cache, in pages no
counter shows, and `/sys/fs/xfs/sda2/stats/stats` (the `buf` line) says
about 7,000 were created by three minutes after boot. That would be cache
the kernel gives back when asked. Not tested yet: a reading before and
after `sysctl -w vm.drop_caches=2` would tell.

With the NVIDIA driver loaded the kernel held 376 MB more, although the GPU
was asleep, and the GPU was awake about 40% of the time with nothing using
it. That is why `tw-gpu` exists.

### What was changed, and what it gave

| Change | Effect |
| --- | --- |
| NVIDIA driver unloaded and the GPU off the bus (`tw-gpu`) | 376 MB of kernel memory |
| `vm.min_free_kbytes=16384`, `vm.lowmem_reserve_ratio = 1024 1024 32 0 0` | held back 285 to 140 MB, and the pages parked per CPU followed from 65–97 down to 39–54 MB: about 170 MB off the figure. `thp_fault_fallback` in `/proc/vmstat` was 0 before; it means something only after days of use |
| `blacklist xe`, `options nvme io_queue_depth=128` | about 5 and 9 MB |
| Xwayland stopped when unused (tw) | 25 MB while no X11 program runs |
| No login manager | the two resident processes (6 MB of their own) and upower; 221 MB while its login screen was left running behind a console session |
| KDE wallet to oo7 | 53 MB resident to 8.8 (8.3 of its own to 1.3) |
| NetworkManager and wpa_supplicant to iwd | 41.6 MB resident to 14.8 (5.7 of their own to 0.4) |
| fnott to `tw-notify` | 27 MB resident (9.5 of its own once used), all session, to nothing unless a notification shows |
| `alsa-plugins` removed | WirePlumber 37.1 MB resident to 24.7 (9.0 of its own to 6.0): one ALSA plugin linked FFmpeg and 79 libraries in |
| `bluetoothd` and the Bluetooth modules off (`tw-bluetooth`) | 6.8 MB resident (0.58 of its own) and 1.6 MB of modules |
| `ananicy-cpp`, `switcheroo-control`, `systemd-userdbd` disabled | 7 MB, under 1, and 2.5 MB of their own (25 MB of lines) |
| power-profiles-daemon to `tw-power`, the accessibility bus kept off, `wl-clip-persist` into tw, boltd to a udev rule | a few MB of their own each, and a process less each |

The owner's readings at startup: about 900, then "like 680" after the
sysctls, then "like 630" with `tw-notify`. Their target is under 500.

### What is left, and what was not done

What a login still holds for itself, outside the one application: tw 19 MB
(Mesa is 14 of it, from the moment the GLES2 renderer exists, in two driver
instances; turning off Mesa's shader cache makes it larger, not smaller),
PipeWire and WirePlumber about 10, the portals 11, systemd's own processes
18, D-Bus 2.9, polkit 2.4, the login and its shell 3.5, oo7 and iwd under 2
together.

Sized but not done:

| Idea | Worth | Why not |
| --- | --- | --- |
| Swap device at 8 GB or 4 GB | 30 or 46 MB | declined. Swap only matters once RAM is full, which on 16 GB a large parallel build does: 8 GB rather than 4 if ever |
| `vm.lowmem_reserve_ratio` at 4096 | 22 MB | not taken up |
| zram replaced by zswap and a 16 GB swap file | about 60 MB (zram's table, 16 bytes per page of the device, held from boot) | declined: builds come first, and once zswap's pool is full it writes to the root disk, an external SSD, where zram never writes at all |
| `vm.percpu_pagelist_high_fraction=1000` | 10 to 60 MB: caps the free pages parked per CPU at about 20 MB, and steadies the reading | declined: more contention on the page allocator in a parallel build |
| `vm.watermark_scale_factor` 10 to 1 | about 65 MB | advised against: the band in which the kernel frees memory in the background shrinks from 16 to 4 MB, and a burst of allocations then stalls the program making it |
| `cgroup_disable=memory` | 5 to 10 MB, estimated | per-service memory accounting goes |
| `transparent_hugepage=never` | lowers the reserve by itself | the owner wants huge pages |
| Portals and PipeWire not started at login | 25 MB at startup only | they start with the first application anyway |
| One GPU driver instance in tw instead of two | uncertain | wlroots opens one for the allocator and one for the renderer |
| Huge pages kept out of tw (`PR_SET_THP_DISABLE`), `malloc_trim()` after startup | at most 1 MB, and 170 kB | tried in a probe, dropped |
| `exec tw-session` | the login shell: 2.5 MB of its own | offered, not tried; quitting tw then logs out |
| No `systemd-timesyncd`, no `systemd-resolved` | under 1 MB of their own each | a clock that drifts; name resolution would need `openresolv` and a trial |
| Void Linux in place of systemd | 9 to 12 MB, estimated | everything in `data/` is built on systemd units; CachyOS's kernel and packages |

Also found: CachyOS's hardware detection puts the NVIDIA modules into the
boot image (`/etc/mkinitcpio.conf.d/10-chwd.conf`), so the driver loads at
every boot before `tw-gpu login` takes the GPU off the bus again. `kvm`
stays loaded because qemu is installed.

## Battery

Measured on battery with the screen at 15% brightness and the Claude app
and a terminal open, by reading the battery's `power_now` every two seconds
next to the i915 interrupt count in `/proc/interrupts` (two per frame
shown) and CPU time. The battery's figure lags what happens by about eight
seconds.

### Before and after

| | Before | After |
| --- | --- | --- |
| Screen still | 11.4 W | 8.1 W |
| The Claude app working (its animation running) | 16.5 W | 8.8 W |

In order of size:

1. **The animation.** At 300 Hz it cost 5 W: the app used 0.8 of a CPU core
   to draw 300 frames a second and tw 0.1 (600 wakeups a second, two per
   frame). The draw follows the frame rate. tw now runs the panel at 60 Hz
   on battery (11.5 to 12.3 W while animating), and the desktop's "reduce
   motion" setting stops the animation altogether: 64 to 78 frames a
   second and 10.8 to 11.8 W with it on, 5 to 6 frames and 8.8 W with it
   off. That setting alone was worth 2 to 3 W.
2. **The Ethernet controller.** It sat fully powered with no cable in
   (`power/control` at `on`, its link's power saving off), and that alone
   held the processor package at its third sleep level. Suspended: 9.74 W
   to 8.29 W at the battery, 2.51 W to 1.13 W in the package, which then
   reaches C6 for 59% of the time.
3. **The power-saver profile**, which KDE used to set on battery and
   nothing did under tw until `tw-power`.

At 54 Wh that is about 6 hours with Claude working, where it was 3.3.

### Where the rest goes

Of 8.1 W idle, the CPU package takes 1.1 W and the GPU nothing. About 7 W
go to what is outside the processor and has no counter: panel and
backlight, the USB system disk, memory, chipset, Wi-Fi. The display does
what it can (PSR1 in self refresh, DC5 entered; DC6 never, which follows
from the package not going past C6; frame buffer compression is off
because PSR1 is on, an Intel workaround). `psys` in RAPL reads 0.23 W and
means nothing on this machine.

The package never sleeps deeper than C6 although the firmware allows C10
(MSR 0xE2 reads 0x74008008: no limit, locked) and the cores are in C10 for
96.6% of the time. Why is a guess: the USB controller is the only part
asking for a short wake-up time (`ltr_show`: XHCI 0.41 ms, the next is
Wi-Fi with 20 ms), and it can never sleep, with the system disk and the
keyboard on it. Not ruled out: some 500 timer interrupts a second with the
Claude app open, and the display. What could tell them apart was not done:
making the chipset ignore the USB controller's request (`ltr_ignore`) with
the root disk on that controller, and letting the keyboard's USB device
suspend. At stake is part of 1.1 W.

Larger than anything left in software: the battery's wear (54 of 90 Wh)
and the system running from the USB disk.

### Other things found

- Already as they should be: the NVIDIA GPU off, keyboard backlight off,
  Wi-Fi power saving on, the unused NVMe disk's link in L1.2.
- CachyOS switches the sound driver's power saving with the cable
  (`/usr/lib/udev/rules.d/20-audio-pm.rules`: 10 s on battery, off on
  mains). The laptop's own sound chip does power down on battery.
- `/etc/udev/rules.d/62-cachy-t7.rules`, owned by no package, keeps the USB
  system disk from being suspended, which is right for a root disk.
- Nothing warned or acted when the battery ran out until tw did: upower was
  only ever started by the KDE login screen.

### Reading the idle draw

What was read, as root, on battery, from an empty workspace with hands off
for half a minute: RAPL, how deep the package sleeps
(`/sys/kernel/debug/pmc_core`), the display's power saving, PCIe link
states and who is awake. Traps met:

- The machine has to be idle while it is measured, or what it says about
  sleep is a lower bound.
- `lspci -vv` wakes the devices that sleep, so look at who is awake before
  listing anything.
- The figures of `package_cstate_show` are microseconds, not TSC ticks.
- The six registers that say how soon the package must be awake again from
  each level (MSRs 0x60A to 0x60C and 0x633 to 0x635) read zero with the
  valid bit clear here: the firmware never set them.

## Sleep

On 2026-11-15 at 16:20:42 tw's idle timer ran out for the first time (15
minutes without input, on mains, the owner away) and tw ran `systemctl
suspend`. The machine did not wake and had to be switched off and on
again. The journal of that boot ends with "PM: suspend entry (s2idle)" and
"Filesystems sync: 0.004 seconds"; it is the only suspend in the 18 boots
the journal held (`journalctl _TRANSPORT=kernel`; `-k` alone only shows the
running boot). Under tw this machine had never been through a sleep and a
wake-up, and the timer was set to 900 seconds all the same. That was the
mistake, and it is why `src/machines/default.h` starts every machine with
sleep off. Nothing held the idle suspend off while the Claude app worked
(it takes only a `delay` inhibitor), which is how a run left alone for 15
minutes was suspended.

Where it stopped is not known: going down, coming up, coming up without
its root disk (a USB disk), or up with a screen tw did not light. Lines
written after a wake-up reach the disk only with the next writeback, so
their absence proves little for the first half minute. The state it slept
in: the NVIDIA GPU off the bus with its sound function still there, the
Bluetooth driver not loaded, the Ethernet controller runtime-suspended,
boltd running. Ruled out: NVIDIA's sleep hook, which exits at once without
the driver. The keyboard is allowed to wake the machine.

What was done: `suspend_after_seconds` and `battery_suspend_percent` are 0
for this machine, so tw sends it to sleep in no case, and `sleep.target`
and `suspend.target` are masked, because the lid (logind's default) and a
typed `systemctl suspend` lead to the same place. So on battery the laptop
runs until it is empty; the warning at 10% is all there is.

Finding the cause would need tests that can each end in another hard
power-off, and none was run: the kernel's dry runs (`/sys/power/pm_test` at
`freezer`, `devices`, `platform`, `processors`, `core`), `pm_trace` to name
the device a hang stops at (it scrambles the clock until the next time
sync), a real sleep ended by the clock (`rtcwake -m freeze -s 30`), and the
same with the GPU switched on, with `deep`, and with the Ethernet rule out.

## Login, keyring and network

How these hang together on this machine; looked up while replacing KDE's
parts, and worth having when one of them breaks.

- **Consoles.** Text consoles come from systemd's getty and depend on no
  login manager. A console left logged in is a shell anyone at the keyboard
  reaches past the lock screen.
- **The lock screen authenticates through `/etc/pam.d/login`**
  (`/etc/pam.d/swaylock` has `auth include login`), the same file a console
  login uses. A mistake there locks the owner out at both; `sudo` uses
  another file. The old file is kept as `login.before-oo7`.
- **oo7** is a user unit (`oo7-daemon.service`, `Type=dbus`), enabled for
  every user (`systemctl --global enable`). `pam_oo7.so` sits in the auth,
  session (`auto_start`) and password stacks as `optional`
  ([system.md](system.md#the-keyring-oo7)); at login it
  hands the password to a helper (`oo7-daemon-login`) that holds it until
  the daemon asks. Keyrings are in `~/.local/share/keyrings/v1/`. Started
  with a wrong password or none the keyring is locked, and a lookup fails
  at once (there is no prompter) and nothing hangs. It took the KDE
  wallet's entries over by itself. 8.8 MB resident, 1.3 MB its own, 21
  threads that do not wake when idle.
- **What the keyring protects.** Its one user so far is the Claude app
  (VS Code and `gh` would use it if signed in). The disk is not encrypted,
  so the keyring is what keeps that token from whoever finds the disk;
  other sign-ins are on the same disk without it
  (`~/.claude/.credentials.json`, `~/.config/gh/hosts.yml`, an SSH key).
- **The switch, 2026-11-15.** iwd connected seven seconds after it
  started, with an address, DNS set in systemd-resolved and power save on.
  oo7 opened from the console login, stored and read back a secret, and
  took the KDE wallet's entries over by itself. Both have booted since.
  Never tried: going back from either, roaming between saved networks.
- **iwd** is set up as in
  [system.md](system.md#wi-fi-through-iwd-instead-of-networkmanager). It
  does nothing for the wired port: that would be systemd-networkd with one
  `.network` file.
- **With KDE and NetworkManager removed** there is nothing to go back to
  here.
- **What is kept on purpose after KDE went:** `vulkan-tools`, `mpv`,
  `ttf-hack`, `ttf-fira-sans`. `heaptrack` keeps `kio` and through it
  `kwallet`, so `ksecretd` stays on disk; nothing starts it. KDE Connect
  stays, with `modemmanager`. `QT_STYLE_OVERRIDE=kvantum` in the fish
  config names a style that is not installed.
- **Thunar** (in Dolphin's place): 52.9 MB resident and 11.2 MB its own
  while a window is open; closing the window ends it. What stays is
  `xfconfd`, 9 MB resident and 0.57 MB its own, until logout. Without
  `gvfs` and `tumbler` it has no trash, mounts no drives and shows no
  thumbnails.
