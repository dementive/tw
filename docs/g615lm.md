# The ROG Strix G615LM

The second laptop the same SSD boots ([g533zw.md](g533zw.md#decisions)):
what it is, what tw does on it, and how the settings made on the G533ZW
fare here. From a probe on 2026-11-19, with the installed tw running and a
monitor plugged in. Its settings in tw are its entry in
[src/machines.h](../src/machines.h).

## The machine

| | |
| --- | --- |
| Model | ASUS ROG Strix G16 G615LM (DMI board name `G615LM`, firmware G615LM.340 of 2026-08-10), Intel Core Ultra 9 275HX: 24 cores, one thread each. 32 GB |
| Panel | `eDP-1`, BOE NE160QDM-NZC, 16 inches, 2560x1600. Two modes: 240 Hz (preferred) and 60 Hz. Adaptive sync from 48 to 240 Hz |
| GPUs | Intel Arrow Lake (`8086:7d67`, `card1`, the boot VGA device, driver `i915`) drives the panel and two DisplayPort outputs, `DP-1` and `DP-2`. NVIDIA RTX 5060 Laptop (GB206M, `10de:2d59`, `card0`, 8 GB, open kernel module 620.70.06) drives `HDMI-A-1`, `DP-3` and an `eDP-2` of its own |
| Battery | holds 77 Wh of the 90 it was designed for; charge limit at 100. Power by the round plug (`ADP0`) or USB-C |
| Power key | right beside the USB ports. Brushed while a mouse was plugged in, it powered the laptop off at once, which `tw-logind.conf` stops ([design.md](design.md#the-session-script)) |
| Thunderbolt | two domains (Thunderbolt 4 generation), security level `user`, `iommu_dma_protection` 1 |
| Wi-Fi and Bluetooth | one Intel BE200 chip: Wi-Fi 7 on PCI (`iwlwifi`), Bluetooth on USB (`8087:0036`), which calls itself Bluetooth as a whole device (class `e0/01/01`) |
| Camera | a USB webcam (`2b7e:c711`, "ASUS FHD webcam", `uvcvideo`) |
| Audio | Intel's (`80:1f.3`), driven by `snd_hda_intel`; the NVIDIA GPU's HDMI sound function besides |
| Ethernet | Realtek RTL8111 (`r8169`) |
| Disk | the G533ZW's external Samsung T7. The internal NVMe disk (Micron, 1 TB) holds Windows, encrypted with BitLocker, and is not mounted |
| Sleep | `s2idle`; the firmware offers `deep` as well. Swap is the 8 GB zram device |

The NVIDIA GPU's `eDP-2` is the panel's second wiring: such laptops have
a switch in the firmware (a MUX) that hands the panel to the NVIDIA GPU.
In that mode the panel would be `eDP-2` on `card0`. `tw-session` would then
pick the NVIDIA GPU, by the built-in panel, and keep it on all session. It
has not been tried, and nothing here needs it.

## GPUs and monitors

`tw-session` takes the Intel GPU first, by the built-in panel
(`TW_SESSION_PRINT=1`, with `WLR_DRM_DEVICES` unset: "first GPU=card1, the
built-in panel"). It adds the NVIDIA GPU only when a monitor is plugged
into it as the session starts, as it was on 2026-11-19:
`WLR_DRM_DEVICES=/dev/dri/card1:/dev/dri/card0`.

A monitor on the NVIDIA GPU was seen working here for the first time on
any machine: a Samsung, 2560x1440 at 60 Hz, through a USB-C hub (VIA Labs,
whose billboard device says it carries DisplayPort). It came up as `DP-3`,
right of the panel. wlroots draws every frame with the Intel GPU and copies
it to the NVIDIA one. Which of the two USB-C ports the hub was in is not
known from `/sys`. The ports wired to the Intel GPU (`DP-1`, `DP-2`) have
not been found either: a monitor there would work when plugged in at any
time and would leave the NVIDIA GPU free to switch off.

After the reboot of 2026-11-19 the same monitor, through the same hub,
came up at 1680x1050: the NVIDIA driver offered nothing larger
(`/sys/class/drm/card0-DP-3/modes` began at 1680x1050, though the monitor's
own EDID still prefers 2560x1440). Before that boot it had offered
2560x1440 and 1920x1080 too. tw takes the best mode it is offered, so the
cause is the link through the hub, which most likely came up with less
bandwidth that time. Unplugging and replugging the hub did not bring
2560x1440 back. An HDMI cable straight into the laptop did: the monitor
came up as the NVIDIA GPU's `HDMI-A-1` at 2560x1440, in the same session.
That it was taken without a new login is because tw had opened the NVIDIA
GPU at that login, for the monitor then on `DP-3`. Use HDMI for this
monitor, not the hub.

Two things it does that looked like faults and are not:

- **A new monitor looks dark.** It shows a workspace of its own, empty,
  and tw draws no background, so it is black until a window goes there or
  the pointer moves onto it.
- **The panel stays on beside it.** Only a closed lid takes the panel out
  of use ([design.md](design.md#the-strip), "The lid").

What the monitor on the NVIDIA GPU costs, with the GPU kept on all session:

| | |
| --- | --- |
| The GPU | awake in P8, 3.4 W and 61 MiB of its memory by `nvidia-smi`, 2 MiB of it tw's. Its sound function still sleeps |
| tw's own memory | 37.8 MB `RssAnon`, against 19 MB in the G533ZW's startup figures with the Intel GPU alone; not measured here without the monitor, and this panel is larger. NVIDIA's EGL libraries are 28.6 MB of tw's resident file pages, mostly shared |
| Each frame | drawn by Intel, then copied to NVIDIA |

A monitor plugged into the NVIDIA GPU after login needs a new login
([setup.md](setup.md#the-nvidia-gpu-off-until-a-program-needs-it)). That
is the design, not a fault: opening that GPU only in case one is plugged
in would cost the above all session.

## Which settings tw uses

The SSD carries one installed tw for both laptops, and tw picks each
one's entry in `src/machines.h` by the board name as it starts (`tw -d`
logs `machine G615LM`). Until 2026-11-19 the build picked a file per board
when it was set up instead, and the installed tw, set up on the G533ZW,
ran the G533ZW's settings here too.

| Setting | Here |
| --- | --- |
| Panel | `eDP-1` at scale 1.25 (2048x1280), the owner's choice. `eDP-2`, its name should the firmware's switch give it to the NVIDIA GPU, at 1.25 too |
| Other screens | scale 1, right of the others |
| Sleep | none: `suspend_after_seconds` and `battery_suspend_percent` at 0 until a suspend by hand has been seen to wake ([Sleep](#sleep)) |

## The G533ZW's system settings here

[g533zw.md](g533zw.md) and [system.md](system.md) list what was changed
outside tw. Checked against this machine:

| Setting | Here |
| --- | --- |
| `blacklist xe` | right: `i915` drives this Intel GPU |
| `options nvme io_queue_depth=128` | applies to the internal disk, which is not used |
| `blacklist ov13858` | no such sensor here; the webcam is on USB and works (`uvcvideo`, `/dev/video0` to `3`) |
| `blacklist kvm_intel`, `kvm` | in force |
| The SOF and AVS audio drivers, kept for this machine | not used for its sound: `snd_hda_intel` drives it, and `snd_sof_pci_intel_mtl` is loaded with no user |
| `blacklist btusb` and the sleep rule | work: no driver, no `bluetoothd`, the adapter asleep (`runtime_status` `suspended`, `control` `auto`) after a boot |

## Battery

Measured on 2026-11-19 on battery, with the screen at 11% brightness
(`nvidia_wmi_ec_backlight`), Claude Code open in foot, and no monitor. Each
quiet window ran 50 seconds, read as root the same way as on the G533ZW
([g533zw.md](g533zw.md#reading-the-idle-draw)): the battery's `power_now`
every 2 seconds (dropping the first 10, since it lags), RAPL, and the
package sleep states from `pmc_core`.

| | Battery | Package |
| --- | --- | --- |
| Idle, with a USB hub holding a Corsair K70 RGB PRO keyboard and a Logitech G502 mouse | 11.9 W | 4.6 W |
| Idle, hub unplugged | 7.05 W | 4.1 W |
| Claude Code working (its spinner animating), hub in | 13.8 W | not read |
| Idle, keyboard and mouse plugged straight into the laptop, no hub (screen at 15%) | 9.2 W | not read |
| Claude Code working, the same | 10.6 W | not read |
| Claude Code working, the keyboard's lights off | 9.9 W | not read |
| Claude Code working, the keyboard's lights off, Claude Code's "Reduce motion" on | 9.25 W | not read |
| Idle, the same | 8.4 to 8.9 W | 5.6 to 5.8 W |
| Idle, the keyboard and mouse unplugged too | 6.94 W | 4.02 W |
| Idle, the same, the laptop's own keyboard allowed to sleep | 6.29 W | 2.90 W |
| Idle after a reboot with `tw-keyboard.rules` installed | 6.6 W | 3.3 W |
| Claude Code working, the same | 7.39 W | not read |

In order of size:

1. **The hub, about 3 W, and the keyboard and mouse, about 2.6 W.** No USB-C
   port was charging, so the battery powered all of them. The hub carries
   DisplayPort, so its converter chip stays powered. The keyboard's lights
   were 0.65 W (turned off with its own brightness key). With the lights
   off, the keyboard and mouse plugged straight into the laptop still cost
   1.95 W, and 1.75 W of that is in the processor, not in the devices: the
   package spent 30% of the time in C2 and 59% in C8 with them, 18% and 75%
   without. Either one alone costs as much as both (package 5.61 W with
   the keyboard alone, 5.52 with the mouse alone, 5.64 with both). Both ask
   to be polled every millisecond (`bInterval` 4 at high speed for the K70,
   1 at full speed for the G502), where the laptop's own keyboard, on the
   same controller and costing nothing extra, asks for 2 and 4. Through the
   DisplayPort hub the package paid only 0.5 W for both, for a reason not
   found, but the hub itself cost 3 W.
2. **Claude Code's animation, 1.4 to 1.9 W.** While it works, Claude Code took
   60 to 80 ms of CPU a second, tw 23 to 27 and foot 5 to 6, for about 35
   to 40 frames a second (68 to 83 i915 interrupts). Its "Reduce motion"
   setting (`prefersReducedMotion`,
   [system.md](system.md#tell-applications-to-keep-still)) stops the
   spinner's shimmer and takes effect at once: 21 i915 interrupts a second,
   Claude Code 55 ms, tw 7.7, foot 1.2, and 0.7 W less. The rest of what
   it costs is Claude Code's own work, not the drawing.
3. **The laptop's own keyboard, 1.1 W.** It is a USB device (the ASUS
   "N-KEY Device", full speed) on the chipset's USB controller, polled
   every 2 and 4 ms, and nothing let it sleep. Allowed to (`power/control`
   `auto`), it slept two seconds after the last key, the controller went to
   D3hot, the package reached C10 for 56% of the time (none before) and
   drew 2.90 W instead of 4.21, and the battery 6.29 W instead of 7.37. The
   first key typed after it slept came through. Intel knows the effect: a
   full-speed USB device kept B660/B760 boards out of C10, with no fix
   ([Intel community](https://community.intel.com/t5/Processors/Poor-power-efficiency-with-B660-B760-boards-and-active-Full/td-p/1565137)).
   tw installs `tw-keyboard.rules` for it
   ([design.md](design.md#the-built-in-keyboard)).
4. **The floor, 6.3 W.** The package draws 2.9 W with the cores at 0.06 W
   and the GPU in RC6 99.9% of the time. The rest of the processor costs
   that much because the 275HX is desktop silicon, with the chipset a
   separate chip. With the keyboard asleep the package is in C10 56% of
   the time and C8 29%; it never enters the S0i2 substates. Under Windows
   a G615 with a 275HX idled at 10.8 W at the wall at best
   ([Notebookcheck](https://www.notebookcheck.net/The-RTX-5080-Laptop-is-optimal-for-Gaming-in-WQHD-Asus-ROG-Strix-G16-G615-review.1005904.0.html)). The other 2.9 W go to the panel, memory,
   chipset, Wi-Fi and the USB system disk, none of which has a counter.

Already as they should be: the panel at 60 Hz on battery (`modetest -p`
shows the CRTC's mode), the saver profile (platform `quiet`, EPP `power`),
the NVIDIA GPU off the bus with its root port in D3cold, PSR2 with
selective fetch in deep sleep while idle (FBC is off because of selective
update, which is i915's rule), DC5 and DC6 entered, the cores in their
deepest state (`C3_ACPI`, MWAIT 0x60, which is C10) all of the time, Wi-Fi
power saving on, and Bluetooth, webcam, Ethernet, Thunderbolt and NPU
asleep.

Tried, as root, and worth nothing:

| Change | Result |
| --- | --- |
| `panel_overdrive` 1 to 0 | idle 8.43 to 8.28 W, within the noise of the reading |
| The GPU's `slpc_power_profile` to `power_saving` (both GTs) | Claude Code working, 9.49 to 9.52 W |
| Turbo off (`intel_pstate/no_turbo`) | Claude Code working, 9.43 W: with Reduce motion on it barely loads the CPU |
| The NPU without its driver, with it, unloaded again | package 5.77, 5.73, 5.77 W: blacklisting the driver costs no power |
| The keyboard and mouse polled every 8 ms (`usbhid` `mousepoll=8`, `kbpoll=7`, devices rebound) | package 5.64 to 5.58 W: the xHCI polls at the interval of the endpoint's descriptor, whatever the driver asks |
| The uncore clock capped at 1.6 GHz (`intel_uncore_frequency` `max_freq_khz`, 3.8 GHz otherwise) | Claude Code working, 11.88 to 11.73 W, package 4.28 to 4.27 W |
| The kernel's `hwrng` thread stopped (`rng_current` from `tpm-rng-0` to `none`) | package 3.31 to 3.16 W, C10 48 to 53%, but the next window, with it back on, read 3.01 W: within the drift |
| Every device's latency request ignored at once (`pmc_core` `ltr_ignore`, then `ltr_restore`) | package 3.01 W, C10 56%: latency requests are not what keeps it in C8 the rest of the time |
| The unused internal NVMe disk taken off the bus (`remove`) | worse: the package stayed in C2 95% of the time, 9.2 W at the battery. Its VMD port went to D3hot, not D3cold. Brought back by a rescan, the disk came without ASPM (every `link/l1*` 0), and the package stayed in C2 until a reboot. Leave it on the bus |

Also looked at:

- **The firmware's package C-state limit.** MSR 0xE2 reads 0x74008008, the
  same as on the G533ZW: no limit, and locked. MSRs 0x60A to 0x635 read
  zero. Why the package never reaches C10 is still not known.
- **What wakes the processor at idle**, from 20 s of kernel tracing:
  about 100 scheduler ticks a second, Claude Code's runtime (Bun's
  `HeapHelper`, `mi-scavenger` and `Collector Thread` threads, about 38
  wakeups a second together while it waits for input), XFS's
  `xfsaild/sda2` (20 a second), the kernel's `hwrng` thread feeding entropy
  from the TPM (`tpm-rng-0`, 9 a second), and one PCI power-event scan a
  second (`pci_pme_list_scan`). Nothing else came close.
- **The system disk's link.** USB 3 lets an idle link doze (U1 and U2),
  and the T7 offers both (exit latencies of 10 and 2047 µs), but both are
  disabled, with the port permitting them and nothing on the system asking
  for that. Asking again (`usb3_lpm_permit`) with dynamic debug on for
  every `xhci_*` function and `hub.c` printed nothing and changed nothing,
  so the kernel declines before it asks the xHCI. Upstream 7.3's source
  has one such silent path: the port's ACPI `_DSM` (function 5) marking it
  unable to do U1/U2, which `xhci_find_lpm_incapable_ports()` reads at
  boot for Intel hosts; it is meant for Type-C ports with retimers. That
  the firmware says so here is likely but not read from the ACPI tables.
  If it does, the link stays awake on this port by design.
- **tw while Claude Code works**, with Reduce motion on: 8 ms of CPU a
  second, about half of it inside i915's ioctls (the profile has no
  symbols: `kptr_restrict` is 2 and the user code has no frame pointers).
  A few hundredths of a watt.

## Memory

At 12 minutes after boot, with Claude Code open, "used" was 1097 MB.
Claude Code itself held 264 MB of that, which leaves about 830 MB against
the G533ZW's 500. Split as in [g533zw.md](g533zw.md#how-to-account-for-it):

| Part | MB | What it is |
| --- | --- | --- |
| Held back | 162 | the watermarks scale with the RAM: each step is 30 MB on 32 GB, twice the G533ZW's |
| Kernel, outside every counter | about 315 | free pages parked per CPU 49 (24 CPUs), module code 38, zram's table 32, the modules' BTF 11, the rest drivers' own pages |
| Kernel bookkeeping | 134 | slab 151 in all, no cache over 12 |
| Shared buffers | 182 | below |
| Programs, Claude Code aside | 41 | tw 13.8, foot 14 |

The shared buffers are what differs most:

| Holder | MB | |
| --- | --- | --- |
| The NPU's driver (`intel_vpu`) | 65.6 | the firmware's working area, 64 MiB by the header of `vpu_37xx_v1.bin`, taken as the driver loads and held all session while the NPU sleeps. Seen as seven shmem objects mapped by `drm_gem_shmem_vmap_locked` in `/proc/vmallocinfo`, a helper only this driver uses here. Nothing installed can use the NPU: its user-space driver is not installed |
| tw's GPU buffers | 61 | two 2560x1600 screen buffers of 16 MB, the terminal's window as a texture, and Mesa's own |
| foot's window | 16 | |
| The text console's framebuffer | 16 | i915 keeps it in RAM here, not in the GPU's stolen memory (128 MB) |
| i915's own objects, tmpfs, the rest | about 23 | |

Outside the counters, the internal NVMe disk, which Linux does not use,
takes 64 MB at every boot: it has no memory of its own and borrows the
computer's for its map of the flash ("allocated 64 MiB host memory buffer"
in the kernel log). `options nvme max_host_mem_size_mb=0` keeps it
([system.md](system.md#module-settings-in-the-boot-image)). With it, "used" without Claude Code was 731 MB after a reboot, with
two terminal windows open (free pages parked per CPU: 51 MB).

So of the 330 MB more than the G533ZW: 66 is the NPU's, 64 the internal
disk's buffer, about 40 the larger panel's buffers, 16 the console's,
about 50 the watermarks and per-CPU pages of 32 GB and 24 CPUs, and the
rest more drivers. The NPU's part and the disk's buffer can go
(`blacklist intel_vpu`, [system.md](system.md#keep-the-npus-driver-out),
and the line above). The console needs its framebuffer for the login, and
the rest comes with the hardware.

The owner took the blacklist the same day. After a reboot the shared
buffers were 129 MB and the unevictable pages 109, down from 182 and 165.
"Used" without Claude Code was 806 MB, but the free pages parked per CPU
were 89 MB that boot, against 49 the boot before; leaving those out, the
saving is about 64 MB. Loading the driver by hand took it back (shared
buffers 117 to 191 MB), and unloading it gave it back again. The NPU draws
no more power without its driver ([Battery](#battery)).

## Sleep

Not tried. As long as neither machine file has a suspend time, tw never
sends this laptop to sleep. The owner's decision to leave sleep off was
about the G533ZW, which did not wake. If a suspend by hand (`systemctl
suspend`, then a key) wakes this one, it can be the machine that
[testing.md](testing.md#seen-on-a-real-machine) says the suspend items wait
for.
